# Review Documentation Impact

変更差分からドキュメント影響を判断し、実装と文書の不一致を残さない。

## Workflow

1. `git diff`と変更対象を読み、外部から観測できる動作、設定、コマンド、公開インターフェース、運用、設計上の制約の変化を列挙する。
2. 変更した識別子、設定キー、CLI引数、API名、エラーメッセージを`rg`で検索し、関連する既存文書と設定例を特定する。
3. 下記の分類に従い、更新が必要な文書だけを選ぶ。
4. Workerは実装と同じTask内で文書を更新する。文書更新が不要なら、変更が内部実装だけで既存の契約・利用方法・設計説明に影響しない根拠を作業報告へ残す。
5. 記載したコマンド、パス、設定キー、API名、既定値、リンクを実装と照合し、可能なものは実行して確認する。
6. Reviewerは差分と文書を独立して照合し、必要な更新漏れや古い記述があれば差し戻す。自明な誤字やリンク修正だけはロール指示の範囲で修正してよい。

## Classification

- README・利用ガイド: セットアップ、CLI、設定、利用方法、利用者向け動作の変更。
- 設定例: 設定キー、既定値、必須項目、環境変数、権限、接続先の変更。
- API文書: 公開API、request・response、エラー、互換性の変更。
- ADR: プロジェクト固有で、将来の変更コストが高い設計判断とその背景。実装の現状説明だけには使わない。
- Knowledge: 現在有効な原則、仕様、制約、失敗回避策。進捗や一時的な作業ログは含めない。
- Skill: 明確な発火条件と複数Taskで反復できる手順。通常の実装Taskから直接昇格せず、Workerが候補を提起しReviewerが根拠と再利用性を確認する。

## Decision Criteria

次のいずれかに該当すれば、原則として文書を更新する。

- 利用者や他の開発者が操作・設定する方法が変わる。
- 公開API、CLI、設定形式、既定値、必要な権限が変わる。
- セットアップ、テスト、ビルド、デプロイ、障害対応の手順が変わる。
- 既存文書の例が動かなくなる、または説明が誤解を招く。
- アーキテクチャ境界、採用技術、重要な制約や判断が変わる。

次だけであれば、文書更新が不要な場合が多い。

- 外部の動作や契約を変えない内部リファクタリング。
- 既存仕様を固定するテスト追加だけの変更。
- コメント、format、命名の局所修正で公開名に影響しない変更。

ただし、既存文書が実装と食い違っていることを発見した場合は、Task範囲で安全に直せるなら更新する。設計判断や要件変更が必要なら推測で直さず、根拠を記録して判断を戻す。

## Report

完了報告に、更新した文書と検証結果を含める。更新不要の場合は「ドキュメント影響なし」だけで済ませず、影響しない契約・利用方法を一文で示す。
